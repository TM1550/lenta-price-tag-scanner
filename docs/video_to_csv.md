# Видео → CSV: распознавание и заполненность полей

Реализован единый запуск `python -m lenta_price_tag_scanner.video_to_csv`. Все модели
работают локально; изображения и база товаров не отправляются во внешние API.

## Актуальные режимы

Текущий default: новые YOLO по видео → трекер → EfficientNet rank → PaddleOCR CPU
→ QR/EAN → каталог → CSV. VLM включается явно. Зафиксированная полная OOF-оценка
с PaddleOCR + Qwen3-VL и EfficientNet off: **154/3701 = 4.1610%**;
[результаты](video_oof_results.md). Она отличается от исторического coverage ниже.

Настройки извлечения полей находятся в `configs/extraction/default.yaml`, геометрия
цен — `configs/price_layout/default.yaml`, обработка изображения и генерация VLM —
`configs/image_processing/default.yaml`. Пример override:
`extraction.name_fraction=0.43 ocr.image_processing.clahe_clip=2.0`.
Вынесение параметров сохранило прежние значения и не является подбором качества.

## Исторический результат полного прогона пяти видео

Файлы на ноутбуке: `data/video_csv_v2/pipeline_final/submission.csv`, `review.html`,
`metrics.json`, `coverage_recomputed.json`, `vlm_ablation.json`, `details.jsonl` и PNG-кропы.
Детектор обработал 1331 кадр, получил 12787 детекций. Фильтры исключили 68 кропов;
432 сегмента дали 430 строк CSV, два сегмента не имели пригодного кропа.

| Показатель                                |   Значение |
| ----------------------------------------- | ---------: |
| Заполнено ячеек / возможных               | 916 / 9890 |
| Заполненность 23 содержательных полей     |  **9.26%** |
| Заполненность с учётом всех 432 сегментов |  **9.22%** |
| Среднее число полей на строку             |       2.13 |

| Скидка                                    |  225 строк |
| Штрихкод                                  |    5 строк |

На **тех же сегментах и кропах**, с теми же правилами объединения и каталогом,
вариант без VLM заполняет 730 ячеек (7.38%). Добавление VLM повышает заполненность
до 9.26%, на 1.88 процентного пункта. Это рост количества предложенных значений,
не доказанный рост точности. QR-поля в этом прогоне не заполнены.
Показатель 916/9890 независимо пересчитан из конечного CSV.

OCR с повторным использованием готовых детекций занял 457.8 с; это не полное время
от видео до CSV. Детекция и OCR запускались последовательно через тот же entrypoint,
с сохранением промежуточных кропов. `detection_config.yaml` хранит параметры детекции,
`config.yaml` — финального OCR. GPU 0 освобождена после выполнения. 15 тестов прошли;
Black/isort/flake8 и проверка Poetry lock выполнены.

## Что проверено на OCR-разметке

Все варианты оценены на одних и тех же **294 изображениях** из пяти видео. Служебные
checkpoint-папки исключены. CER/WER рассчитываются по полной транскрипции после
нормализации регистра и пробелов. Меньше — лучше. Данные использованы для выбора
решения: это development benchmark, а не нетронутый финальный test.

| Вариант                                            |        CER |        WER |
| -------------------------------------------------- | ---------: | ---------: |
| EasyOCR RU/EN, CPU                                 |     0.7706 |     0.9729 |
| PP-OCRv5 mobile + east-Slavic recognizer, CPU      |     0.7038 |     0.8988 |
| PP-OCRv5 Cyrillic + выравнивание и CLAHE, CPU      |     0.7148 |     0.8866 |
| PaddleOCR-VL 0.9B, GPU                             |     0.7111 |     0.8436 |
| **Qwen3-VL-4B, исходный вариант**                  | **0.5869** |     0.7261 |
| Qwen3, раздельное чтение верхней и нижней половины |     0.5883 |     0.7281 |
| Qwen3, выравнивание и CLAHE                        |     0.6020 |     0.7521 |
| Qwen3, повышенное минимальное разрешение           |     0.5871 | **0.7217** |

Улучшения CER относительно прежней Qwen3 не получилось. Небольшое изменение WER
при повышенном разрешении не даёт основания объявлять общий рост качества.
Меньшая PaddleOCR-VL занимает около 1.90 GiB выделенной PyTorch GPU-памяти против
8.40 GiB у Qwen3, но на этих кропах заметно хуже. Время сохранено в JSON; некоторые
эксперименты выполнялись одновременно, поэтому их wall time нельзя считать строгим
сравнительным бенчмарком скорости.

Снимки конфигураций, транскрипции и метрики каждого эксперимента сохраняются в
`data/ocr_experiments_v2`. Общая сводка — `ocr_comparison_v2.json`.
Консервативные фильтры качества сохранили все 294 уже отобранных размеченных кропа.
Выбор одного наиболее резкого/крупного кадра на каждую из 107 track-групп дал Qwen3
CER 0.5420; выбор первого кадра тех же групп — 0.5387. Это **не улучшение** от
ранжирования и не сравнение с тем же набором из 294 изображений.

Часть эталонных текстов включает обрезанные на изображении слова, поэтому низкий CER
ограничен качеством исходного материала и согласованностью аннотаций. Следующий
осмысленный шаг — проверить эталоны, собрать больше полностью видимых ценников и
разметить строки/поля для обучения и оценки по видео. Дообучение OCR здесь не проводилось.

## Итоговая схема

1. YOLO на каждом третьем кадре, затем BoT-SORT с компенсацией движения камеры.
2. Разрыв сегмента при большом скачке bbox, паузе более секунды или длительности
   более 10 секунд. Это защитные эвристики, не доказательство правильной идентичности.
3. Фильтры минимального размера, контраста, резкости и почти полного пересвета/темноты.
   Резкость измеряется после приведения короткой стороны к 160 пикселям. Все причины
   отбраковки записываются в `filter_audit.jsonl`.
4. Отбор top-K кадров на сегмент по резкости и размеру. По умолчанию K=3; проверенный
   полный прогон использует K=2. Сохраняются PNG без дополнительной JPEG-компрессии.
5. PaddleOCR читает текст и координаты строк; zxing отдельно декодирует QR/EAN.
6. Поля разных кадров объединяются только при совпавшем штрихкоде или близком названии.
   При конфликте цен поле остаётся пустым. Совпадающие пиксели не дают повторный голос.
7. Опционально Qwen3 читает лучший кадр сегмента. Её результат сохраняется отдельно,
   а подстановка/замена названия фиксируется в происхождении полей.
8. Только однозначное точное совпадение валидного кода с каталогом заменяет название.
   Нечёткие совпадения остаются предложениями. Цен в каталоге нет: из него они не берутся.
9. Создаются CSV, подробный JSONL, метрики и страница визуальной проверки.

EfficientNet подключается через `efficient_weights=.../model.pt`; нужны новые веса
с RGB-метаданными. По умолчанию этот фильтр выключен: предыдущая OOF-проверка показала
recall 0.529. Включение строгого фильтра без учёта потерянных ценников завышает впечатление
от результата. Его порог задаётся `efficient_threshold`.

Одна строка CSV соответствует **сегменту трека**, а не гарантированно уникальному
физическому ценнику. Сегментация защищает от смешивания товаров, но может создавать
дубли. Для заявления о точности tracking/dedup нужна отдельная разметка идентичностей.
Первый ByteTrack-прогон смешивал товары под одним ID и сохранён только как диагностический
baseline. Незавершённый вариант с чрезмерной фрагментацией не используется как результат.

## Запуск

Из корня репозитория, Python 3.12:

```bash
poetry install --with ocr,paddle,vlm
poetry run python -m lenta_price_tag_scanner.video_to_csv videos=../data yolo_weights=../lenta-price-tag-scanner/base_pipeline/price_tag.pt detector_device=cuda output=data/video_result top_k=2 vlm_fallback=true vlm_limit=1000 vlm_name_override=true
poetry run python -m scripts.review_video_csv data/video_result
```

GPU выделяется через `CUDA_VISIBLE_DEVICES=0` в окружении процесса. Для CPU без VLM:

```bash
poetry run python -m lenta_price_tag_scanner.video_to_csv detector_device=cpu vlm_fallback=false output=data/video_cpu
```

На сервере всё находится в `/home/ozon_hack/lenta-ml-system`. Сначала выполните
`source environment.sh` и `export CUDA_VISIBLE_DEVICES=0`, затем перейдите в `project`.
Вместо `poetry run python` используйте `../.venv-paddle/bin/python`, а для YOLO задайте
`yolo_weights=../models/price_tag.pt`. Paddle окружение отделено от основного; используется
PaddleOCR 3.3.2 / PaddlePaddle 3.2.2. Все кеши расположены внутри выделенной папки.
GPU 1 не используется. Веса скачиваются только при первом запуске.

Параметры: `stride`, `pattern`, `max_frames` (0 означает всё видео), `top_k`, `tracker`,
`quality.*`, `ocr.backend`, `ocr.preprocess`, `vlm_fallback`, `vlm_backend`, `vlm_limit`,
`vlm_name_override`. Поворот кропа задаётся `rotation_ccw=90` для текущих видео.
Поддерживаются OCR backends `easyocr`, `paddle`, `qwen`, `paddlevl`.
Для VLM как основного backend задайте также `ocr.device=cuda`.

Папка результата должна быть новой. `detection_only=true` сохраняет только детекцию
и выбранные кропы. Затем можно повторять OCR без YOLO:

```bash
poetry run python -m lenta_price_tag_scanner.video_to_csv resume_tracks=data/detection_run/tracks.json output=data/ocr_repeat vlm_fallback=true
```

Цены из неподписанных цифр произвольно не назначаются. `price_template_field=price_card`
включает эвристику крупной цены с копейками для известного шаблона; она может ошибаться
на других типах ценников. Отключение: `price_template_field=`. `details.jsonl` помечает
такие значения как `price_template_heuristic`.

## Метрика заполненности

CSV содержит 29 столбцов схемы Lenta. Шесть полей — служебные: имя видео, timestamp
в миллисекундах и четыре координаты. Они не участвуют в основной метрике.

`coverage = число непустых содержательных ячеек / (число строк × 23)`.

Пустая строка, null/None, `нет`, `nan`, `unknown`, `n/a` не считаются распознаванием.
Дополнительно выводятся количество заполненных полей по столбцам, среднее число
полей на строку, разрез по видео, отдельная заполненность 12 основных и 11 QR-полей.
`coverage_all_detected_tracks` использует в знаменателе все обнаруженные сегменты,
включая исключённые фильтрами; `track_retention` показывает долю выданных строк.

Повторный расчёт по готовому CSV:

```bash
poetry run python -m lenta_price_tag_scanner.field_extraction data/video_result/submission.csv --output data/video_result/coverage_recomputed.json
```

Заполненность **не является точностью**: неверное название тоже непустое. Это не scorer
хакатона и не доказательство выполнения целевой метрики >0.04 из заявки проекта.
Правильность цен, названий и всех остальных полей нужно измерять по ручной разметке полей.

## Источники проверенных подходов

- [PP-OCRv5 multilingual, документация авторов](https://www.paddleocr.ai/main/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.html).
- [PaddleOCR-VL, модель и пример Transformers](https://huggingface.co/PaddlePaddle/PaddleOCR-VL).
  Использована зафиксированная ревизия `7fa00a8c55b735ba51ba49a9058f3f9c57a99a11`.
  Для её custom code адаптировано только название аргумента causal mask под Transformers
  4.57; смысл маски не менялся. Код модели не изменяется на диске.
- [Ultralytics: BoT-SORT, ByteTrack и параметры](https://docs.ultralytics.com/modes/track/).
- [Решение LentaTech команды «Медвежата»](https://github.com/LinaDugau/LentaTech): отбор
  кадров, OCR/QR и каталог. Опубликованные авторами результаты не переносились на наш набор.
- [lenta_price_vision](https://github.com/kostr-code/lenta_price_vision): сочетание tracking,
  OCR/VLM и нескольких кропов. Это источники архитектурных приёмов, не гарантия качества.
