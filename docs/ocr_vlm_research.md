# OCR/VLM: найденные решения Lenta Tech 2026

Проверено 2 ноября 2026 года. Ниже — опубликованные реализации и обзор организаторов; места команд и качество чужих моделей независимо не проверялись. Чужой код в проект не копировался.

## Что делали участники

1. [kostr-code/lenta_price_vision](https://github.com/kostr-code/lenta_price_vision): YOLO + ByteTrack, top-K кропов на трек, Qwen2.5-VL, PaddleOCR как дополнительный источник и отдельное декодирование QR/штрихкода. VLM возвращает структурированные поля. В [реальном модуле VLM](https://github.com/kostr-code/lenta_price_vision/blob/master/pipeline/vlm.py) используется transformers, разбор JSON и приведение названий полей; [промпт](https://github.com/kostr-code/lenta_price_vision/blob/master/prompts/qwen_extract.md) задаёт геометрию полей и null для отсутствующего результата. Это пример прямого image-to-fields, а не подтверждённого поиска VLM по каталогу. README называет 3B, default dataclass в модуле — 7B; конфигурацию нужно сверять, а не копировать вслепую.

2. [LinaDugau/LentaTech](https://github.com/LinaDugau/LentaTech): YOLO с tiled-инференсом, трекинг, несколько лучших кропов, EasyOCR/PaddleOCR, QR/barcode; Qwen2.5-3B используется как текстовая LLM для product_name. Это не то же самое, что VLM, читающая изображение. Далее результат сопоставляется с db_hack.csv. В [match_to_catalog.py](https://github.com/LinaDugau/LentaTech/blob/main/ml/scripts/match_to_catalog.py) fullname/code преобразуются в name/barcode, сначала применяется lookup по коду. Для каталогов более 20 тысяч строк этот скрипт отключает fuzzy-поиск по названиям. В коде есть восстановление цен из расширенного каталога и эвристики; их нельзя переносить на наш CSV, где цен нет. Это полезный пример структуры, а не доказательство корректности всех правил.

3. [letmly/lenta-shelf-control](https://github.com/letmly/lenta-shelf-control): описан путь через ByteTrack, зональный PaddleOCR, QR и голосование по нескольким наблюдениям. Сам README предупреждает, что код является заготовкой. Поэтому это источник идей, а не проверенное готовое решение.

[Разбор организаторов](https://habr.com/ru/amp/publications/1059038/) подтверждает пользу трекинга, отбора кадров, зонального OCR, QR и сопоставления с каталогом. Условия хакатона подразумевали локально разворачиваемый пайплайн без внешних облачных API. Мультимодальные модели применялись, но не заменяли проверку структуры и согласованности полей. Это не основание автоматически приписывать отдельному открытому репозиторию призовое место.

## Что есть в наших данных

Локально проверен data/db_hack.csv: Windows-1251, 625172 строки данных, поля fullname и code. Считать code строкой, чтобы не терять ведущие нули. Поле code в каталоге нельзя автоматически приравнивать к одноимённому полю итогового CSV: в результате хакатона code означает код зоны выкладки, а репозиторий участника трактует каталоговый code как штрихкод. Перед внедрением проверить соответствие по известным товарам, длины и контрольные цифры EAN, дубликаты и неоднозначность.

Из этой базы нельзя получить текущую цену, скидку, дату печати или QR-поля. База позволяет предложить каноническое название и идентификатор товара. Наличие файла и опубликованные примеры подтверждают техническую возможность локального использования; отдельный доступ к серверу базы не требуется.

## Предлагаемый эксперимент для нашего проекта

Baseline: текущие кропы → EasyOCR RU/EN → зональный парсер → QR/штрихкод → точное сопоставление с каталогом → CSV. Сначала измерить результат без каталога, затем с каталогом на тех же отложенных видео.

VLM-вариант: локальная Qwen2.5-VL читает только видимые поля из кропа и возвращает JSON. Для выбора товара сначала извлечь OCR/QR-код либо выполнить поиск по названию в локальном индексе (например SQLite FTS); передавать VLM только короткий список кандидатов и изображение. Не помещать все 625 тысяч записей в промпт. Разрешить ответ «нет уверенного совпадения», сохранять исходное чтение, выбранный код, score и источник каждого поля. Эта схема — предложенный эксперимент, не установленный факт о решении победителей.

При точном совпадении кода можно заполнить fullname; при текстовом совпадении дополнительно проверять бренд, объём/массу и вариант товара. Цены брать с изображения или декодированного QR. Отдельно измерять долю ложных совпадений каталога: неверное уверенное исправление может ухудшить итоговую метрику.

Перед сравнением OCR и VLM нужен одинаковый набор кропов и одна схема оценки. Новые models/API сейчас не устанавливались и текст не извлекался: выполнены исследование и подготовка входов. Для промышленного CSV ещё нужны связывание наблюдений одного ценника и агрегация по треку.
